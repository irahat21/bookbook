# Assumptions, decisions, deviations and mocks

Source of truth: `docs/BookOrbit_AI_Phase2_Design_Report.pdf` (v2.0), use cases
UC-01..UC-18 and business rules R1..R15 (Table 2). The Phase I SRS that the report
cites (`Phase1_Specification.pdf`) is not in `docs/`, so the Phase II report is used alone.
`docs/SRS.md` is a plain-text extract of the PDF (headings, UC/R IDs and pseudo-code kept;
diagrams left out) so it can be searched without PDF tools.

Status legend: **RESOLVED** (decided with the project owner), **ASSUMPTION** (our reading
of something the SRS leaves open), **DEVIATION** (we knowingly differ from the SRS
pseudo-code), **FLAG** (kept as written but worth noting), **MOCK / STUB** (not the real thing).

## Gaps filled

| ID | Gap | Status | Decision |
|----|-----|--------|----------|
| A-08 | UC-01 only creates Registered Customers; how is a Super-User created? | **RESOLVED** | `seed.py` creates the Super-User account (`sue_admin`). |
| A-09 | May a customer review the same book more than once? | **RESOLVED** | One review per customer per book (enforced in `ReviewService.submit`, UC-10). Seeded reviews follow this. See A-21 for blocked reviews. |
| A-10 | R15: summarize / explain / ask on non-owned books do not check the chapter | **RESOLVED** | R15's chapter-1 limit applies to *every* Reading Companion action (done, Phase 3): summarize / quiz of chapter > 1 raise "Buy the book to keep reading", and for a non-owned book Ask / Explain only retrieve chapter-1 excerpts. Test: `test_r15_applies_to_every_action` (checked by removing the limit: the test fails). |
| A-11 | Book texts and covers | **RESOLVED** | Generated locally by `seed.py`. Nothing is downloaded. All 50 books are made up. Covers: abstract PNGs. Texts (Phase 3): 10 books, one per category, have a hand-written original text in `seed_texts/` (3 chapters of 400-600 words each, `CHAPTER n: Title` layout, checked by `tests/test_texts.py`); `seed.py` copies them to `data/texts/<book_id>.txt` and sets `text_path`. They stand in for the "public-domain text" of R15. The other 40 books have no text, so UC-14 E1 can be shown. `seed_texts/policies.txt` (copied to `data/policies.txt`) restates R1-R15 in plain words for the chatbot's POLICY chunks (SRS 4.21). |
| A-12 | `keywords` is typed `str` but the recommender loops over it | ASSUMPTION | Stored as a comma-separated string ("family, secrets"), split on commas where a list is needed. Keyword search matches keywords + description (SRS 4.8). |
| A-13 | UC-13 E3 "lists example admin questions" has no pseudo-code | ASSUMPTION | Done (Phase 3). An ADMIN question that matches none of the seven admin fact topics gets a fixed list of example questions (`chatbot.ADMIN_EXAMPLES`) instead of the pseudo-code's "all facts". Because the SRS keyword list maps almost one-to-one onto the facts, "admin" and "report" are added to the ADMIN keywords so E3 can actually happen ("Give me an admin report"). The chat screen also shows example questions for every role. |
| A-14 | "My Orders" and "My Reviews" sidebar items have no use case | ASSUMPTION | My Orders = the customer's purchases; My Reviews = their reviews (blocked ones shown only as "blocked - never shown") and their warnings (UC-11 step 3). Done in Phase 2. |
| A-15 | `browse_count` (R3) counts every view | ASSUMPTION | Counts views by everyone (Visitors and SUs included), as UC-05 step 3 says; only RC/VC views create a BROWSE_EVENT. |
| A-16 | UC-04 cover search returns the top 5; text search ordering when a sort is chosen | ASSUMPTION | Text search keeps best-match order (exact, prefix, contains) unless the user picks a sort other than title. Cover search shows up to 5 covers, most similar first, each with its similarity; covers below the threshold are left out, so E4 ("best similarity below the threshold") shows "No matching cover found". |
| A-17 | Year search input format | ASSUMPTION | A single year (`1995`) or a range (`1990-2000`). |
| A-19 | "Rounded to the cent" (R6, SRS 3.1) does not say how | ASSUMPTION | Half a cent rounds **up** (`bookorbit/money.py`, `Decimal` + `ROUND_HALF_UP`). Python's `round()` rounds exact halves to even and works on binary floats, so `round(0.125, 2)` is 0.12 and `round(2.675, 2)` is 2.67. Example: VIP discount on $12.45 = $1.245 -> **$1.25**, pays $11.20. Every amount written to a file goes through `cents()`. |
| A-20 | UC-08 step 2: what the confirmation dialog shows when the balance is too low | **RESOLVED** | The dialog shows list price, VIP discount, amount to pay **and the current balance**. If the balance is too low it warns that confirming will be rejected with a $1.00 fine (R7), and, if the fine would take the balance below $0, that the account would be suspended. R7 itself is unchanged: confirming still charges the fine (F-18). Helper: `PurchaseService.quote` (not in the SRS; it only reads). |
| A-21 | Does a **blocked** review use up the customer's one review of that book (A-09)? | **RESOLVED** | No. Only a PUBLISHED review counts, so after a block the customer may write a new review; the warning is the penalty. |
| A-22 | The SRS gives no taboo word list | **RESOLVED** | `seed.py` seeds 10 mild placeholder words (no real profanity, it is a class demo): crap, darn, dumb, garbage, heck, idiot, lame, moron, stupid, trash. "dumb" is the SRS prototype's own example. Super-Users will edit the list in UC-16 (Phase 4). |
| A-23 | Demo data for R10 | **RESOLVED** | `seed.py` adds `wes`, an RC whose two blocked reviews gave him 2 warnings, so a single blocked review shows a suspension live. `victor` covers VIP demotion. |
| A-25 | Verified-buyer weight (R12) when a customer reviews first and buys later | ASSUMPTION | The weight is fixed when the review is submitted, as in the pseudo-code (`ReviewService.submit`): a review written before buying stays at weight 1.0. Combined with one review per book (A-09), that customer cannot later get weight 2.0 for that book. |
| A-26 | R5 "more than 3 purchases" / "more than $200" | ASSUMPTION | Read literally: the **4th** purchase promotes (3 is not enough), and spending must exceed $200.00 (exactly $200.00 is not enough). Book prices are $4.99-$34.99, so the purchase-count path almost always triggers first. Counters restart at 0 after a demotion (R10), not after a reopen (R8 only resets warnings). The discount starts with the purchase *after* the promotion (R6, UC-09 E2). |
| A-27 | The MOCK language model cannot read a prompt | ASSUMPTION | `LLMClient.generate` takes extra keyword hints (`task`, `context`, `question`) that only the MOCK reads; the real Ollama client ignores them because the same information is in the prompt. The services build the SRS prompts in every mode, so switching `LLM_MODE` changes nothing else. Code: `bookorbit/ai/llm.py`. The MOCK's STORE/GENERAL classifier (SRS 4.20 `classify_intent`, last step) cannot judge meaning, so the chatbot gives it the best-matching store chunk as a hint: a question that matches a policy or catalog chunk counts as STORE. |
| A-28 | `LLMClient.is_available` (SRS 4.22) only checks that `/api/tags` answers | ASSUMPTION | We also check that both configured models (`OLLAMA_MODEL`, `OLLAMA_EMBED_MODEL`) are pulled; otherwise Ollama "is available" but every call fails. A `:latest` tag matches the bare name. |
| A-29 | `MIN_SIM = 0.45` (SRS 4.21) is tuned for nomic-embed-text | ASSUMPTION | The MOCK's word-count vectors give lower similarities for the same relevance (a short question shares only a few words with a 250-word chunk). Measured on the seeded data: relevant policy / catalog chunks scored 0.20-0.52, unrelated questions ("capital of France", "bake a cake") 0.00-0.147. So `MIN_SIM_MOCK = 0.15` (`bookorbit/ai/rag.py`); real mode keeps 0.45. To make the mock usable, it hashes words into 2048 slots (512 gave collisions, e.g. "capital of France" matched a romance blurb) and ignores the word "book", which is in almost every chunk. |
| A-30 | `RAGRetriever.build_index` details | ASSUMPTION | (1) Each chunk records the `embed_model` that made its vector; if the model changes (MOCK <-> Ollama) the whole index is rebuilt, because vectors of different models can't be compared. (2) Books with a text and `indexed = false` are indexed at every start, not only when the index is empty (UC-15 E4). (3) A book without a CATALOG chunk gets one. (4) The CATALOG chunk also lists the book's keywords. Built in a background thread at start-up; the sidebar shows "Preparing AI index…" meanwhile (SRS 4.24). |
| A-31 | `admin_context` details (UC-13) | ASSUMPTION | "This month" = the calendar month of `clock.now()` (so seeded October sales do not count in November). A fact is relevant when the question contains one of its topic words (`chatbot.ADMIN_TOPICS`, e.g. "suspend", "sales"/"revenue", "balance"); "order lists" without "no"/"to" shows both lists. Customer keywords match where the SRS says "contains", starting at a word boundary ("fine" does not match "define", "my purchase" matches "my purchases"). |
| A-32 | Reading Companion details (UC-14) | ASSUMPTION | Define uses the first word of the selection (no selection: "Select a word first"). Quiz JSON is read from the outermost `[...]` because real models often wrap it in text or a code fence; invalid questions are dropped (SRS), one retry, then "Couldn't make a quiz - try again". The MOCK quiz needs a few sentences of 8-35 words; a one-sentence chapter gets that message (`test_quiz_on_a_one_sentence_chapter_gives_a_clear_error`); every seeded chapter gives 3 questions. Opening a non-owned book always starts at chapter 1 even if a later chapter was saved. "Buy the book to keep reading" shows a Buy Now button that runs the same Buy Now flow as the book page (`BuyMixin`) and returns to the companion. |
| A-33 | Cover index details (SRS 4.9, UC-04) | ASSUMPTION | (1) The SRS E4 threshold 0.25 (`rules.COVER_MIN_SIM`) is for OpenCLIP; the MOCK has its own, measured like A-29: photos of a seeded cover scored >= 0.80 with it, faces / noise / a blank page <= 0.62 with every cover, so `COVER_MIN_SIM_MOCK = 0.70`. The seeded Clockmaker photo (darker, rotated PNG) scores 0.77, the closest to the line. (2) `data/covers/index_model.txt` records the embedder; a different one re-embeds every cover at start-up. (3) Built at start-up in the same background thread as the RAG index. Requires Pillow (in `requirements.txt`) to read JPG photos. |

## Deviations from the SRS pseudo-code

| ID | Where | Status | What and why |
|----|-------|--------|--------------|
| D-15 | `AuthService.is_locked` (SRS 4.6), R2 | **DEVIATION** (done, Phase 1) | The pseudo-code checks "the last 3 attempts all failed within 5 minutes". After a lock expires, the 3 old failures are still the last 3, so one more failure re-locks at once. We replay the attempts in order and reset the counter after a success **or** after a lock expires, so the user gets 3 fresh tries. Code: `AuthService.lock_state`; test: `test_lock_expiry_gives_three_fresh_tries`. |
| D-16 | `ChatbotService.ask` (SRS 4.20) | **DEVIATION** (done, Phase 3) | `classify_intent` may call the LLM before `is_available()` is checked, so the bot would crash when Ollama is offline. We check availability first; offline, intent uses the keyword rules only. |
| D-17 | `ChatbotService.ask`, Visitor with no store context | **DEVIATION** (done, Phase 3) | The pseudo-code returns "I couldn't find that..." labelled source `RAG`. The Petri net (UC-12 P10) says "store questions only". We return the P10 message with source `DENIED`. |
| D-18 | `RAGRetriever.retrieve` for whole-chapter tasks (SRS 4.21/4.23) | **DEVIATION** | Summarize and Quiz retrieve with the query "summary of chapter n" / "key events of chapter n". That text resembles no chunk, so the MIN_SIM cut-off would drop the whole chapter. `retrieve` takes `min_sim`; the Reading Companion passes 0 for summarize / quiz / define, so it gets the top-k chunks of that chapter. Tested in `test_book_and_chapter_filters`. If retrieval finds nothing (index still building, or no excerpt similar enough), the companion uses the current readable chapter's own text, so answers stay grounded in the book. The companion also checks that the LLM is available *before* retrieving (offline, the embedding model is gone too), like D-16. |
| D-19 | `RecommendationEngine.personalized` (SRS 4.10), R4 | **DEVIATION** | The pseudo-code keeps books with `score > 0`, but `score` adds `0.1 x weighted_avg` as a tie-breaker, so every rated book scores > 0: an unrelated 5-star book would be "recommended" and E2's popular fill would almost never happen. We keep only books that match the profile (category, author or keyword points > 0); the tie-breaker still orders them. Test: `test_d19_unrelated_rated_book_is_not_a_match` (fails with the pseudo-code's rule). |

## Flags

| ID | Rule | Note |
|----|------|------|
| F-18 | R7 | Kept exactly as written: a customer with $0.00 who clicks Buy is fined $1.00, the balance becomes -$1.00 and the account is **suspended at once**. Strict, but it is what the SRS says. The seeded user `sid` is in that state (created by a real purchase attempt). The Buy Now dialog now warns before this happens (A-20). |
| F-24 | R10 order of checks (SRS 4.16 `apply_consequences`) | **QUESTION FOR THE GROUP.** The pseudo-code checks "is VC -> demote" *before* "RC with > 2 warnings -> suspend" and returns after the demotion. So a VIP who already has 2 warnings and gets a 3rd blocked review is **only demoted** (now an RC with 3 warnings, still ACTIVE); the *next* blocked review suspends them. R10 can also be read as "the 3rd warning always suspends". We kept the pseudo-code order; test: `test_vip_with_two_warnings_only_demoted`. If the group decides otherwise, the fix is to check the suspension first in `WarningService.apply_consequences`. |

## Mocks and stubs (also shown in the UI)

| ID | What | Status | Details |
|----|------|--------|---------|
| M-01 | Biometric sign-in (UC-01, UC-02, R1, R2) | **MOCK** (`BIOMETRIC_MODE=mock`) | No webcam / microphone / PyTorch. The user picks a sample *file* (PNG/JPG photo or WAV clip). The mock turns it into a unit vector: a fixed random "person" vector plus a small per-file offset. Two different samples of the same person score about 0.92 cosine and different people about 0.0, so the real R2 thresholds (0.60 face / 0.75 voice), the lockout and E3/E5/E6 all behave as specified. The person comes from a PNG text tag written by `seed.py` (any other photo is identified by its file hash); for voice it is the clip's dominant pitch. Templates are stored as `.npy` files exactly as in the SRS. Real models: Phase 3 (optional). The sidebar shows "MOCK biometrics". |
| M-02 | Personalized recommendations (UC-06, R4) | **DONE** (Phase 3) | `RecommendationEngine.personalized` / `build_profile` / `score` as in SRS 4.10 (with D-19). Home shows "Recommended for You"; the Recommendations screen also shows why each book was picked and the customer's top interests. This is a real (simple, content-based) recommender, not a mock: it needs no model. |
| M-03 | Cover-image search (UC-04 step 4) | **MOCK** (`COVER_MODE=mock`, Phase 3) | `bookorbit/ai/covers.py` `MockCoverEmbedder`: a colour histogram + an 8x12 thumbnail instead of OpenCLIP. It finds cropped / tilted / brightened / JPEG photos of our generated covers (tested on every seeded cover: 250 of 250 found first), but it knows nothing about what a cover shows. Sample photos: `data/samples/covers/` (3 cover photos, `not_a_cover.png` for E4, `not_an_image.txt` for E3). The camera button is disabled with a tooltip while the index is built or if the model is missing (E5). The catalog status line says MOCK cover search. |
| M-04 | VIP price on the details page (UC-05 step 5) | **DONE** (Phase 2) | Was a stub in Phase 1; now `CatalogService.get_details` uses `PurchaseService.final_price`. |
| M-05 | Screens for later phases | **STUB** | Sidebar items for later phases (Phase 4 admin screens) open a placeholder naming the phase and use case. Since Phase 3 the AI Chatbot and the Reading Companion are real screens; the companion button is disabled only for books without a text (UC-14 E1). |
| M-06 | Seed data | **Real services** (since Phase 2) | Deposits, purchases, `victor`'s VIP promotion, `sid`'s fine and suspension, `wes`'s warnings and all seeded reviews go through the real services, so counters, ledgers, verified weights and status changes are consistent. `clock.frozen()` gives them fixed, repeatable timestamps. Only users, books, biometric templates and taboo words are written directly. Seeded reviews are clean text. |
| M-07 | Reopening a suspended account (R8, UC-17) | **STUB** until Phase 4 | `StatusManager.can_reopen` / `reopen` exist and are tested, but the Super-User screen that calls them comes in Phase 4. Until then a suspended customer can deposit (and sees "a Super-User can now reactivate your account" once the balance is >= $0) but stays suspended. To reset the demo, run `seed.py`. |
| M-08 | Language model and embeddings (SRS 4.22; used by UC-12, UC-13, UC-14) | **MOCK** (`LLM_MODE=mock`) | Ollama is not installed. `bookorbit/ai/mock_llm.py`: embeddings are a hashed bag of words (2048 numbers; texts sharing words are similar, so retrieval works, but it knows no synonyms). Answers are **extractive**: the best-matching sentences of the retrieved facts; summaries = the chapter's most "typical" sentences; quizzes = fill-in-the-blank with 4 options; Explain / Define quote the passage's neighbours / the sentence using the word. It never invents text. The sidebar shows "MOCK AI". `LLM_MODE=real` uses Ollama (falls back to this MOCK, labelled, if Ollama or a model is missing); `LLM_MODE=offline` imitates a stopped Ollama to demo the offline messages. |
| M-09 | Real cover search (`COVER_MODE=real`, OpenCLIP) and real biometrics (`BIOMETRIC_MODE=real`, YOLOv8-face + FaceNet + Resemblyzer) | **WRITTEN, NOT TESTED** | The code exists (`OpenClipEmbedder` in `bookorbit/ai/covers.py`, `RealBiometricEngine` in `bookorbit/ai/biometrics.py`) behind lazy imports, but the packages (`requirements-real.txt`, unpinned) and the YOLOv8 face weights were never installed, so it has **never run**. Without them both modes fall back to their MOCK and the label says why (`tests/test_real_modes.py`). Real biometrics still read a chosen photo / WAV file, not a live camera or microphone. **Switching to real biometrics means re-enrolling everyone:** the saved templates in `data/biometrics/` are MOCK vectors. They have the same sizes as the real ones (512 face, 256 voice), so nothing crashes and no "template missing" (UC-02 E6) appears; every comparison just quietly scores near 0, and users get "Not recognised" and are locked after 3 tries (R2). The seeded sample "faces" are cartoons a real face detector will probably not find (UC-02 E5), and the voice clips are pure tones, not speech, so real voice embeddings of them are meaningless (different demo users might even look alike). So with real biometrics, demo users must register again with real photos and recordings; the seed data is for MOCK mode only. Unlike the RAG and cover indexes (A-30, A-33), biometric templates do not record which model made them. |
